# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

WebLens is a premium web intelligence API running on **Cloudflare Workers** with **Hono** as the web framework. It provides web scraping, search, extraction, and research tools, monetized via the **x402 micropayment protocol** (HTTP 402 Payment Required with on-chain USDC verification). The live API is at `api.weblens.dev`.

External API dependencies: **SerpAPI** (web search), **Anthropic** (AI extraction/research), **Firecrawl** and **Zyte** (fallback scraping providers), **Cloudflare Browser Rendering** (JS rendering, screenshots).

## Architecture

### Runtime & Framework
- **Cloudflare Workers** with `nodejs_compat` flag
- **Hono** web framework with typed `Env` bindings and `Variables` context
- **ES modules** (`"type": "module"`, target ESNext, bundler module resolution)
- **JSX** configured for Hono (`jsxImportSource: "hono/jsx"`)

### Entry Point & Middleware Chain (`src/index.ts`)
Global middleware applied in this order, then route groups registered:

1. Logger → CORS → Request ID (also creates the request-scoped structured logger) → Security Headers → ERC-8004 receipt (paid calls only) → POST-only enforcement (for `PAID_ENDPOINTS` array) → path-template guard → 405 method guard. Global errors are caught by `app.onError(errorHandler)` (idiomatic Hono) — **not** a `*` middleware — and the 404 by `app.notFound`.
2. Route groups registered in order: System → Reader → Free → Credits → Paid (every endpoint in the registry, see below)

The Durable Object class `CreditAccountDO` is re-exported from the entry point for Workers binding.

### Key Directories
- **`src/endpoints/`** — **the paid endpoint registry, the single source for every paid route.** One `defineEndpoint({...})` per endpoint, grouped in `pages.ts` (fetch/render/extract/crawl), `search.ts`, `intel.ts`, `billing.ts`: path, title, description (≤500 chars), catalog tags, Zod `input` + `inputExample`, `outputSchema` + `outputExample`, a `PriceModel` (`resolve(body)` plus the advertised `min`/`max`; builders `fixedPrice`, `perUnitPricing`, `complexityPricing` in `define.ts`), optional `cacheKey`, `acceptsCredits`, `evmOnly`. Definitions are data only, so any module can import the catalog without the handlers. `index.ts` derives `ENDPOINTS`, `PaidPath`, `PAID_ENDPOINTS` and `EVM_ONLY_PAID_PATHS`. The advertised input schema is generated from the Zod schema (`requestBodySchema()`, `z.toJSONSchema` in input mode), so field `.describe()` text in `schemas.ts` is what buyers read.
- **`src/routes/`** — `paid.ts` registers every registry endpoint with one middleware stack and binds each path to its handler in a `Record<PaidPath, Handler<AppEnv>>` (a missing or extra handler does not compile). The other files register free and system routes (system, reader, free, credits).
- **`src/tools/`** — Endpoint handler implementations. Each tool is a Hono handler that reads `validatedBody` from context, calls services/external APIs, and returns a flat domain object plus `requestId` and a per-endpoint ISO timestamp field (`fetchedAt` / `searchedAt` / `extractedAt` / `analyzedAt` / etc.).
- **`src/services/`** — Business logic layer (pricing, caching, credits DO proxy, content hashing, AI/Anthropic integration).
- **`src/middleware/`** — Middleware factories: payment (x402 lazy-init singleton), credit-middleware (wallet signature auth + debit), validation (Zod), rate-limit (IP-based via KV), cache, security, error handler.
- **`src/durable_objects/`** — Cloudflare Durable Objects. `CreditAccountDO` manages atomic credit transactions via key-value Durable Object storage (`ctx.storage.get/put` — not the SQL API), exposes `/deposit`, `/spend`, `/balance`, `/history` internal endpoints. Keeps max 100 transactions (LIFO).
- **`src/schemas.ts`** — All Zod request validation schemas. Reusable primitives: `urlSchema`, `timeoutSchema`, `limitSchema`. Includes bounds (viewport 320-3840px, timeout 5-30s, cache TTL 60-86400s).
- **`src/config.ts`** — Centralized pricing, network/facilitator config, cache settings, viewport bounds, timeouts. All prices defined here. **Pricing floor rule:** every SerpAPI-backed endpoint (search family, verticals, transcript) costs $0.009–$0.015 upstream per call depending on plan tier — never price those below $0.015. `/answer` bundles a SerpAPI call + a capped Claude call (~$0.017 worst case on Haiku 5.5) — keep its price ≥ 2x that. **Every AI step uses `AI_MODEL` (`config.ts`, Claude Haiku 5.5, $0.10/$0.50 per MTok up to 100k-token prompts) through the one client `callClaude()` (`services/ai.ts`), which disables thinking (callers' output caps and cost ceilings are priced on the visible answer) and reads the text block, not `content[0]`.** Anthropic retires models on a schedule (`claude-sonnet-4-20250514`, which `/extract` hardcoded, was retired 2026-06-15 and every paid `/extract` then failed): check platform.claude.com/docs/en/about-claude/model-deprecations when touching AI code. **Two pricing tiers exist and must not be confused:** endpoints with a paid upstream (SerpAPI/Anthropic) carry a real cost floor, but native-fetch endpoints (`/fetch/basic`, `/contents`, `/map`, `/crawl`, `/pdf`) cost ~$0.000001-0.00002 per call because Workers bills $0.30/M requests + $0.02/M CPU-ms and **does not bill subrequests at all** — those are priced to win on price, not to clear a floor. Browser Rendering endpoints (`/fetch/pro`, `/screenshot`) sit between at $0.09/browser-hour. Per-unit resolvers format to **4 decimals**: at a sub-$0.001 unit price, 3 decimals rounds odd counts up and overcharges.
- **`src/types.ts`** — All TypeScript interfaces: `Env` (Worker bindings), `Variables` (Hono context vars), request/response types, `ErrorCode` enum.
- **`src/openapi.ts`** — OpenAPI 3.1 spec, Scalar UI at `/docs`, and `/llms.txt`. Every paid operation and every llms.txt endpoint section is **generated from the registry** by `src/endpoints/docs.ts` (`openApiPaidPaths()`, `llmsEndpointSections()`, `llmsMcpToolLines()`); only free/system ops and the guide prose are hand-written here. The spec doubles as the **x402scan discovery document** (`/openapi.json`): `info.x-guidance`, per-op `x-payment-info` (`paymentInfo()`: fixed when `min === max` and not cacheable, else dynamic from the cache-discounted min to the max), `security: []` on free/auth-gated ops, and request `example`s so registration probes can reach the 402 challenge. x402scan's prober builds a body from each REQUIRED property's `example` (then `format`, then the string "test"), so `endpointBodySchema()` copies every property's value from the definition's validated `inputExample` into the schema; `tests/unit/openapi-discovery.test.ts` enforces it. Per-endpoint usage notes for llms.txt live in each definition's `guide`, extra error responses in `errors`.

### Hono Context Variables
Middleware stores state in Hono context (`c.set()`/`c.get()`):
- `requestId` — UUID generated at ingress
- `validatedBody` — Zod-parsed request body (set by validation middleware, consumed by handlers)
- `paidWithCredits` — boolean flag; when `true`, x402 payment middleware is skipped
- `startTime` — `Date.now()` for `X-Processing-Time` header calculation
- `log` — request-scoped structured `Logger` bound with `requestId`/method/path; use `c.get("log").info("event.name", {fields})` (set by Request ID middleware, always present)
- `cacheHit` / `cacheKey` / `cacheTtl` / `cachedBody` — set by the cache middleware (see Caching)

### Adding a New Endpoint
Add a `defineEndpoint({...})` to the right group in `src/endpoints/` and its handler to `HANDLERS` in `src/routes/paid.ts`. `registerPaidRoutes` builds the same stack for every paid route:
```
[cacheLookupMiddleware]        // only with cacheKey; runs first so both money paths see the hit
validateRequest(input)         // Zod validation → sets validatedBody
createCreditMiddleware(price)  // only when acceptsCredits
createLazyPaymentMiddleware    // x402 payment wall, advertising the definition's schemas and tags
[cacheServeMiddleware]         // only with cacheKey
handler
```
The order is **validation → credit → payment → handler** on every paid route: invalid bodies are rejected before any money moves, and both money middlewares can read `c.get("validatedBody")`. Handlers read `c.get("validatedBody")` (no per-handler re-parse) and `c.get("requestId")`. The definition's ONE `PriceModel` feeds BOTH the credit debit and the x402 challenge (`routePrice()`; cacheable endpoints are wrapped in `cacheAwarePrice()`). The only difference is the **x402 floor**: the x402 challenge charges `x402Charge(price)` = max(price, `PRICING.x402Minimum`, $0.004), because every x402 sale pays the facilitator a settle fee (PayAI Base $0.00231 once its free allowance is spent), while a credit debit settles nothing and pays the list price. Every advertised x402 price (`x-payment-info` via `x402PriceBounds()`, `describePrice()`'s "an x402 payment is at least $0.004" note, `productPriceRange()`) includes the floor. A price whose `min` equals its `max` is passed as a string so the payment wall can cache its middleware. `tests/unit/endpoint-registry.test.ts` checks every definition (examples validate, resolved prices lie inside the advertised range, descriptions ≤500 chars, output examples use declared fields) and `tests/workers/paid-routes.test.ts` checks every route's real 402 against its definition. Free endpoints use `rateLimitMiddleware` + `validateRequest` with their own free-tier schemas (exported from `src/tools/free.ts`).

### Payment System (x402 Protocol)
- Client sends POST without payment → gets 402 with price/network/address
- Client signs USDC transfer, retries with `Payment-Signature` header (x402 v2)
- `@x402/hono` middleware verifies on-chain, request proceeds
- Payment middleware uses **lazy initialization** — `getResourceServer()` creates a singleton on first request, cached at module scope in `src/middleware/payment.ts`
- Static pricing middleware is also cached; dynamic pricing (for extract/fetch-pro) re-evaluates per request via callback
- **Facilitators come from config, one ordered chain per network family**: `FACILITATORS_EVM` and `FACILITATORS_SVM` in `wrangler.toml` (`cdp,payai` / `payai` in production, `x402.org` on testnet; vars are not inherited, so both envs declare both). `facilitatorPlans()` (`src/middleware/payment.ts`) builds them, and `getResourceServer()`, `/health` and `facilitatorNames()` all read it. x402ResourceServer gives each (scheme, network) to ONE facilitator at `initialize()` and never retries elsewhere, so each family is wrapped in a `FacilitatorChain` (`src/services/facilitator-chain.ts`): it advertises its family's kinds from the first facilitator that answers `/supported` and verifies/settles through each in turn until one succeeds. Each handover is recorded in the request's funnel event (`fallback` column, e.g. `cdp settle: unable_to_estimate_gas`) — the funnel is unsampled, unlike the `facilitator.fallback` / `facilitator.exhausted` log lines (Workers Logs keep ~10% in production) — because `facilitator` names only the one that finished: a sale PayAI rescued would otherwise read as a plain PayAI sale and hide CDP's failure rate. `pnpm run funnel` prints settle reliability per facilitator (settled / settled + handed over + failed, all payers) and the absorbed failures by reason. **Base settles through CDP first** (the CDP Bazaar indexes and ranks a route only by CDP-settled payments, and CDP carries ~83% of x402 buyers) **and PayAI takes over** a payment CDP fails on (coinbase/x402#1065). That fallback is sound only because EVM `exact` requirements are facilitator-independent (both advertise it with an empty `extra`, verified 2026-10-13, and `ExactEvmScheme.enhancePaymentRequirements` ignores the kind) and an EIP-3009/Permit2 nonce can be spent once, so a second settle cannot double-charge. **Solana stays PayAI-only**: the quote carries the facilitator's own fee payer (CDP `BFK9…`, PayAI `CjNF…`), so `parseFacilitatorOrder` refuses a second Solana facilitator. A configured facilitator without credentials (`cdp` without CDP keys) throws instead of being skipped. CDP refuses payments below its minimum (`amount_too_low`: a cached $0.0006 was refused, $0.0015 settled) — the $0.004 x402 floor keeps every quote above it. Default URLs live in `FACILITATOR_URLS` (`config.ts`). The chains are logged at init (`x402.init_ready`, e.g. `facilitators: "eip155: cdp > payai; solana: payai"`, plus `payaiApiKey`). `/health` probes each facilitator once and returns 503 only when the cache is down or a network family has no reachable facilitator left. **PayAI API key** (`PAYAI_API_KEY_ID` + `PAYAI_API_KEY_SECRET`, `src/services/payai-auth.ts`): PayAI settles free only within an allowance counted per payout wallet (drawn from a shared pool for requests from cloud IPs) and from prepaid credits beyond it (Base EIP-3009 settle = 2.31 credits = $0.00231; Solana 1.52). With both halves set, `/verify` and `/settle` carry an EdDSA JWT (`kid`/`sub` = key id, `iss: payai-merchant`, 120s lifetime, re-signed 30s before expiry); `/supported` stays public. PayAI rejects a bad credential instead of downgrading to anonymous, so half a key attaches nothing, and deleting either secret is the kill switch. The key was vended 2026-10-13 over x402 (`POST merchant.payai.network/api/v1/keys/vend?amount=5`, 5,000 credits) by the WebLens Ops wallet, which owns the PayAI account: key recovery (`/api/v1/keys/recover`) is SIWx with that wallet, and `GET /api/v1/account` with the same JWT shows the credit balance. Both halves are in the personal vault. **Multi-network:** `config.ts` no longer hardcodes a network list. `evmNetwork(env)`, `svmNetwork(env)` and `supportedNetworks(env)` derive it, so a network can never be advertised on a discovery surface while the wall cannot take money on it. EVM is always on; **Solana is gated on `PAY_TO_ADDRESS_SVM`** and `getResourceServer` registers `ExactSvmScheme` only when it is set — registering a network the facilitator does not advertise on `/supported` leaves `initialize()` with no supported kind and `buildPaymentRequirements` then throws for every request on the route. Solana needs no SOL and no RPC: PayAI settles it with a sponsored `feePayer` from its `/supported` `extra` (`CjNFTjvBhbJJd2B5ePPMHRLx1ELZpa8dwQgGL727eKww` on mainnet), and the USDC mint defaults from `@x402/svm`. The payout address **must already have a USDC associated token account** — the SVM `exact` spec makes the facilitator verify the destination exists. Discovery reports CAIP-2 ids (`eip155:8453`), not `"base"`, so an agent can match them against `accepts[].network`. Every surface that names networks — `/discovery`, `/.well-known/x402`, `/mcp/info`, the ERC-8004 document, and the "USDC on …" prose in `/openapi.json`/`llms.txt` — derives them from `supportedNetworks(env)` / `supportedNetworkNames(env)`; never hardcode a chain name. **Solana is live in production since 2026-10-07** (`PAY_TO_ADDRESS_SVM` = the Phantom wallet's Solana address; its USDC ATA `BVo3EAd4…VbrFq` must never be closed). **`EVM_ONLY_PAID_PATHS` (`/credits/buy`) never offers Solana**: credit accounts are EVM wallets and the handler reads the payer from the EIP-3009 `authorization.from`, which a Solana payload does not have.
- **Payment funnel telemetry** (`src/services/payment-telemetry.ts`): every paid-route request that reaches the x402 wall produces **exactly one** event, written to the `PAYMENT_EVENTS` **Workers Analytics Engine** dataset (adaptively sampled even at our volume, so `pnpm run funnel` totals are `SUM(_sample_interval)` estimates and revenue is counted on-chain; 3-month retention; dataset names in `PAYMENT_EVENTS_DATASETS`, pinned to `wrangler.toml` by a test) and to the structured log (`x402.<outcome>`, payer `mask()`ed). Outcomes: `unpaid`, `v1_header` (an x402 v1 `X-PAYMENT` buyer we cannot serve), `rejected` (pre-verify), `verify_rejected`, `verify_error`, `settled`, `settle_failed`, `canceled`, `wall_unavailable`, `unclassified`. The typed x402 hooks in `getResourceServer` only *record* into an `AsyncLocalStorage` `PaymentAttempt` opened around the wall; `createLazyPaymentMiddleware` emits the single event. **A facilitator rejection (HTTP 200 `isValid:false`) never reaches `onVerifyFailure`** — it arrives as a normal verify result, so `onAfterVerify` is what records it. Facilitator clients are wrapped in `TrackedFacilitatorClient` so each event names the facilitator that verified/settled. Report: `CLOUDFLARE_ACCOUNT_ID=… CLOUDFLARE_API_TOKEN=… pnpm run funnel` (token: *Account Analytics: Read*; `EXCLUDE_PAYERS` drops the canary payer).
- `@x402/core` background init calls `process.exit(1)` on `FacilitatorCapabilityError`/`RouteConfigurationError`. **Measured in workerd (2026-10-13): it cancels the in-flight request (500 "process.exit(1) API was called. Canceling the request.") but the isolate survives** — the next request is served with module state intact and reaches the existing wall-failure handling (cache eviction, retry, 503).

### Credit System (Alternative to Per-Request Payment)
Three-layer architecture:
1. **Credit middleware** (`src/middleware/credit-middleware.ts`) — intercepts `X-CREDIT-WALLET` header, verifies the EIP-191 wallet signature via `verifyWalletSignature()` (one-directional timestamp window: ≤5min old, ≤60s future skew) with KV-backed **replay protection** (each signature consumed once via a `sigreplay:` nonce in CACHE), then attempts debit. On insufficient funds, gracefully falls through to x402 payment. **Refunds:** handlers report failures by returning JSON error envelopes (not throwing), so the middleware refunds the debit both when `next()` throws AND when the final `c.res.status >= 400` — refunds are idempotent via the `refund:${requestId}` externalId. Success responses carry `Payment-Method: Credits` + `Credit-Cost`; refunded ones carry `Payment-Method: Credits` + `Credit-Refunded`.
2. **CreditAccountDO** (`src/durable_objects/CreditAccountDO.ts`) — atomic balance management per wallet. Tiers: standard → premium ($100 deposited) → enterprise ($1000). Transaction history capped at 100 entries.
3. **Credit service** (`src/services/credits.ts`) — DO proxy functions. Bonus tiers: 20% at $10, 30% at $50, 40% at $100+ (descending sort for highest applicable match).

### Error Handling
- Registered via `app.onError(errorHandler)` (`src/middleware/errorHandler.ts`) — idiomatic Hono; catches throws from any middleware/handler regardless of order, logs the error through the structured logger, and returns the envelope. `ERROR_CODE_MAP` does substring matching on the message → `ErrorCode`.
- Consistent envelope: `{error, code, message, requestId, retryAfter?}` where **`error` always equals `code`** (machine-readable); human text goes in `message`. New codes must be added to the `ErrorCode` union in `types.ts`.
- Status mapping in `getHttpStatus()`: 400/401/402/404/405/413/422/429/500/502/503.

### Logging & Observability (`src/utils/logger.ts`)
- Structured JSON to `console.*` (Cloudflare Workers Logs auto-indexes the fields — no logging lib). `createLogger`/`loggerFromEnv(env)`/`mask()`; levels gated by `env.LOG_LEVEL`, mapped to `console.error/warn/log` for severity.
- Request path uses `c.get("log")`; DOs use `loggerFromEnv(this.env)`; services take an optional `Logger`. Event names are dotted (`credit.debit`, `provider.fallback`). **Never log** secrets/signatures/raw headers; `mask()` wallets. `wrangler.toml [observability]` on with `head_sampling_rate` (0.1 prod / 1 testnet).

### URL Validation & SSRF (`src/services/validator.ts`, `src/utils/safe-fetch.ts`)
- `validateURL()` **canonicalizes** IPv4 literals in any encoding (dotted/octal/hex/shorthand/bare-int) and range-checks against private blocks; also blocks non-canonical encodings, RFC1918/loopback/link-local/CGNAT, IPv6 loopback/ULA/link-local, embedded credentials, `.onion`, and non-HTTP(S) schemes. Returns `{valid, normalized?, error?}`.
- `safeFetch()` re-validates **every redirect hop** (manual redirect) — use it for any fetch of a user-supplied URL (all fetch tools + provider-registry native path do).
- Browser-rendered endpoints (`/fetch/pro`, `/screenshot`) can't use `safeFetch` — Chromium follows redirects itself — so `hardenPage()` (`src/utils/browser-guard.ts`) enables Puppeteer request interception and re-validates **every request the page makes** (navigation, redirect hops, subresources) against `validateURL()`. Any new Puppeteer usage must call `hardenPage(page)` right after `newPage()`.
- The validation middleware rejects bodies over 256KB (`MAX_BODY_BYTES` in `src/middleware/validation.ts`) before parsing; `cacheLookupMiddleware` enforces the same bound because it parses the body first on cacheable routes.

### Free Previews (`src/services/previews.ts`, `POST /preview`)
Answers "is this worth paying for?" before the 402 — the measured ecosystem failure is agents probing and never buying. Returns the price for the caller's own body plus a recorded response sample. **Cost rule: a preview must never cost us money.** Only `LIVE_PREVIEW_ENDPOINTS` (no paid upstream — native fetch only) may run a real truncated preview; SerpAPI/Anthropic-backed endpoints always return the recorded sample. Samples and summaries come from each registry definition (`outputExample`, `previewSummary`), and `describePrice()` from its `PriceModel`, so every paid endpoint has a preview by construction; a test asserts no live-preview endpoint has a paid upstream. The rule covers **every free route**: `tests/workers/free-routes-cost.test.ts` drives `/r/*`, `/free/fetch` and `/preview` (for every paid endpoint) through the real Worker with `globalThis.fetch` spied, and fails if any request reaches a host in `PAID_UPSTREAMS` (`config.ts`). Free search (`/free/search`, `/s/*`) was removed for spending the SerpAPI quota the paid search family depends on.

### ERC-8004 (`src/services/erc8004.ts`, `src/middleware/receipt.ts`)
WebLens hosts the **off-chain half** of ERC-8004, which is what the spec permits an operator with no contracts to do: the registration document at `/.well-known/agent-registration.json` (`registration-v1`), per-paid-call receipts at `/receipts/{requestId}` (buyer's `proofOfPayment` evidence — for x402 calls the receipt's network, transaction and payer come from the settled `PAYMENT-RESPONSE` and its price/payTo from the buyer's accepted requirement, never from env, so a Solana payment is recorded as Solana; `X-Receipt-Id`/`X-Receipt-Url` headers on paid responses), and `POST /feedback`, which stores a buyer-authored feedback document verbatim and returns the `feedbackURI` + keccak-256 `feedbackHash` pair that `giveFeedback()` takes. Documents are served byte-identically so the buyer can recompute the hash.

**Do not overclaim:** WebLens is not registered on-chain, holds no agent id (`registrations` is deliberately `[]`), and writes to no registry. Receipts are unsigned: their evidence is the settlement `transaction` (plus `payer`, `payTo`, `network`), which anyone can check on-chain. (An HMAC `mac` was removed with ACV proof-of-context: only WebLens could verify it, and with no `SIGNING_PRIVATE_KEY` set it was keyed by the CDP API secret.) Receipts are only written for calls that were paid *and* served (2xx), so probes cannot fill KV. `viem` supplies keccak-256 and is a **runtime** dependency (also used by `utils/security.ts` for wallet signature verification) — it was previously misfiled under devDependencies.

### Deep Research (`src/services/deep-research.ts`)
`/research/deep` runs plan → search-per-sub-question → fetch/dedupe → cited synthesis in **one synchronous call** (same rationale as `/crawl`). Priced per depth tier (`quick`/`standard`/`deep`) via `PRICING.deepResearch`; `DEEP_RESEARCH_TIERS` in `config.ts` fixes the bounds that keep cost under price, and `describeDeepResearchTiers()` renders them for every surface (`quick` = one search on the question as asked, no planning call; it replaced the old `/research` endpoint) — **changing a tier's `subQuestions`/`maxSources` changes the cost floor, so reprice with it** (a test asserts price > worst-case cost). Planning and synthesis run on `AI_MODEL` (Haiku 5.5) with hard output caps and per-source truncation. Expect **30–60s** wall-clock — document a generous client timeout. Degrades rather than failing a paid request: planning falls back to the raw query, a failed search is skipped, a failed fetch falls back to the search snippet, and non-JSON synthesis is served as prose.

### Company Profile (`src/services/company-profile.ts`, `POST /company`)
A domain → a sourced company profile, read live from the company's own site (incumbents sell account-gated database snapshots). One call: `inspectDomain` + `/.well-known/security.txt` start at once; robots.txt is fetched **per origin** (a redirect to `www.` has its own rules) and checked before every page; the homepage's own links are classified into about/pricing/careers/contact by path (`classifyPages`, shortest path wins); the careers page, or the conventional `/careers` when none is linked, is read with a larger cap (`COMPANY_PROFILE.maxCareersHtmlBytes`, 4 MB: Vercel embeds its Greenhouse data 1.32 MB into a 1.4 MB page) only to find the job board; homepage + about + pricing go to ONE capped `callClaude` pass whose JSON is validated field by field (`parseAiProfile`: off-schema values dropped, and a `source` survives only if it is a page the model was given, compared as normalised URLs). Hiring comes from the public **Greenhouse / Lever / Ashby** board APIs (`src/services/job-boards.ts`, unauthenticated, verified 2026-10-13; link shapes from real careers pages; Lever/Ashby return full descriptions, so boards get `maxBoardBytes` 16 MB — Palantir's Lever board is 6.1 MB). Company-level facts only: no people, no personal contacts. Failures are errors so a paid call is cancelled, not sold: robots-disallowed homepage → 403, unreadable homepage or non-JSON model reply → 502, AI down → 503. Cacheable (`cacheKey: "company"`). Shared helpers it introduced: `services/site-pages.ts` (`fetchSitePage`, `pageHrefs`, `findSocials`, also used by `/intel/project`), `fetchRobots` in `services/crawler.ts` (also `/crawl`), `BOT_USER_AGENT` and `CACHE_TTL_SECONDS` in `config.ts`, and `utils/narrow.ts` (`isRecord`, `asRecords`, `str`, `num` for reading parsed JSON without casts).

### Provider Chain (`src/services/provider-registry.ts`)
`/fetch/resilient` tries the native `safeFetch` scraper first, then re-fetches through **Cloudflare Browser Rendering** (`hardenPage` applied) for client-rendered pages and sites that refuse bare HTTP clients. The response reports which tier served it. The chain previously listed "Firecrawl → Zyte via x402", but that path returned "not yet implemented" on 402 and both advertised endpoints 404 — the endpoint was charging 5x `/fetch/basic` for plain fetch plus two doomed requests. Adding a real third-party tier would require WebLens to hold a funded wallet and sign outbound x402 payments; don't advertise such a tier until it actually settles.

### Crawling (`src/services/crawler.ts`, `src/tools/map.ts`, `src/tools/crawl.ts`)
- `/map` discovers URLs without fetching content: robots.txt `Sitemap:` directives → `/sitemap.xml` → nested sitemap indexes (bounded by `CRAWL_LIMITS.maxSitemapDocs`) → homepage link extraction as fallback. Real sites nest — both developers.cloudflare.com and x402.org serve a sitemap *index*, so index recursion is mandatory, not optional.
- `/crawl` is a **bounded synchronous** same-host BFS returning markdown per page. Deliberately not an async job: polling would need either a free status endpoint (abuse vector) or a second payment, neither of which fits x402's one-shot-per-request model. Workers paid plans allow 10k subrequests/invocation and bill CPU only (not network wait), so a 1–25 page crawl fits comfortably. Batched at `CRAWL_LIMITS.concurrency`.
- Billing: the caller pays for the **requested page budget** (`limit × PRICING.crawl.perPage`), not pages returned — one resolver feeds both the credit debit and the x402 challenge.
- Safety: same-host only, every discovered link re-validated through `validateURL()` before fetch (link/sitemap data is attacker-controlled), all fetches via `safeFetch`, non-HTML content types rejected, and robots.txt honoured by default (`respectRobots: false` opt-out; start URL disallowed → 403 `FORBIDDEN`).

### Probe-Friendly Validation (`src/middleware/validation.ts`)
Unauthenticated POSTs to a path in `PAID_ENDPOINTS` (`src/endpoints/index.ts`, also used by the POST-only middleware) **skip** body validation and fall through to the x402 payment middleware, so the caller gets the 402 challenge instead of a 400. Rationale: such a request can never reach the handler (payment middleware always 402s it), and production logs showed ~170 bare probes to `/intel/site-audit` bouncing as 400 — the exact "Expected 402, got 400" failure x402scan documents. Requests carrying `Payment-Signature` or `X-CREDIT-WALLET` keep strict validation so money never moves on an invalid body; the 256KB cap still applies to everyone. Covered by `tests/unit/validation-probe.test.ts`.

### Caching
- Opt-in via the `cache` body field (default `true`) on every endpoint with a registry `cacheKey` (the fetch family and `/company`; the schema fields are the shared `cacheOptions` in `schemas.ts`); implemented in `src/middleware/cache.ts` + `src/services/cache.ts`. On a hit the cached body is served (handler skipped) and the 70% discount applies to both the credit debit and the x402 challenge.
- Cache keys: `weblens:{endpoint}:{sha256(sorted_params)[:12]}`
- TTL clamped to `CACHE_TTL_SECONDS` (60-86400s; default 3600s)
- 70% discount on cached responses (`PRICING.cacheDiscount`)
- KV-backed via CACHE namespace

### Dynamic Pricing (`src/services/pricing.ts`)
- `getComplexityMultiplier()` analyzes URLs: HIGH_COMPLEXITY_DOMAINS (Twitter, Facebook, LinkedIn, Amazon, Booking, Airbnb) get 3.0x multiplier
- Deep paths (>3 segments) or many query params (>2) get 1.5x
- `calculatePrice()` returns 4-decimal precision for USDC atomic units
- `productPriceRange()` (`src/endpoints/index.ts`) derives the advertised x402 price range from the registry's product endpoints (after the cache discount and the x402 floor) — no hardcoded range strings
- `getCachedPrice()` applies the 70% cache discount; used by the cache middleware's `cacheAwarePrice()`, which wraps both money paths

### Discovery & Bazaar (`src/tools/discovery.ts`, `src/openapi.ts`)
- `/discovery` — machine-readable `SERVICE_CATALOG` for autonomous agent discovery; its `services` are the registry's product endpoints (every group except "Credits")
- `/.well-known/x402` — standard x402 discovery endpoint
- `/openapi.json` — x402scan discovery document (register at x402scan.com/resources/register; requires `info.x-guidance` + per-op `x-payment-info` + `security: []` on free ops per x402scan.com/discovery/spec)
- Uses `@x402/extensions/bazaar` (`declareDiscoveryExtension` in `src/middleware/payment.ts`) — this got WebLens indexed in the **PayAI facilitator discovery catalog** (facilitator.payai.network/discovery/resources, **14** resources as of 2026-09-03; PayAI indexes more broadly than settles alone — 12 of the 14 carry a `lastUpdated` of 2025-11-30, predating any payment, while `/search/places` and `/research/deep` were refreshed within ~15s of their settlements).
- **Why WebLens is absent from the CDP Bazaar — it is not a config defect.** CDP's `POST /platform/v2/x402/validate` (public, needs no API key, and the single best diagnostic here) reports `valid: true`, `simulation: accepted`, **25/25 preflight checks passed** and `index: null` for every endpoint. Per [CDP's seller docs](https://docs.cdp.coinbase.com/x402/seller/get-discovered) there is no registration call: a resource enters the catalog only after **the CDP facilitator itself settles a payment for it**, and indexing is **per-resource** — one payment never covers sibling routes sharing a `payTo`. Until 2026-10-13 WebLens kept PayAI primary (CDP's Base-mainnet `/settle` failed intermittently — x402-foundation/x402#1065), so buyer payments were settled by PayAI and CDP saw none; Base now settles through CDP first (see the facilitator chain above), so every Base sale counts toward the listing. Verified on-chain: both real payments (0.35 USDC 2026-08-13 = `deepResearch.deep`; 0.045 USDC 2026-08-31 = `places`) emitted EIP-3009 `AuthorizationUsed` and were relayed by **PayAI's** Base relayers `0xc6699d2a…`/`0xb2bd2992…` (attribution: facilitators.x402.watch), batched through Multicall3. Real revenue therefore does *not* imply CDP indexing. (#2112, the old "CDP never emits `EXTENSION-RESPONSES`" indexing bug, was **closed 2026-07-16** — no longer a blocker.)
- **Canary payments and CDP seeding** (`scripts/canary-payment.ts`, `pnpm run canary`): pays on `PAY_NETWORK=base|solana` (EVM_PRIVATE_KEY / base58 SVM_PRIVATE_KEY of a dedicated burner wallet — never a payout wallet) through the production facilitator path (Base: CDP first, PayAI fallback; Solana: PayAI), to prove a settle path end-to-end, measure settle reliability, and seed CDP Bazaar listings (any settled Base canary indexes its route); it prints the payer so `pnpm run funnel` can exclude it with `EXCLUDE_PAYERS`. The funnel shows which facilitator settled each payment, and `facilitator.fallback` log lines show the CDP failures the fallback absorbed. (The old `X-Bazaar-Bootstrap` per-request CDP path and its `BAZAAR_BOOTSTRAP_SECRET` were removed once CDP became the Base default.) The script **plans by default and pays only with `CONFIRM=yes`**, builds request bodies from the published bazaar `input` example (with `cache: false` on cacheable endpoints: a cache hit skips the handler and charges the discounted price, which CDP refuses as `amount_too_low` — a cached $0.0006 `/fetch/basic` was refused, $0.0015 and $0.002 settled), reads each price from that endpoint's own live 402 **for that exact body** (never hardcoded), caps spend via `MAX_PRICE`/`MAX_TOTAL`, retries #1065 failures, and reports the resulting CDP `index` state for Base payments. Measured plan at `MAX_PRICE=0.02` (2026-10-13): 19 endpoints for **$0.1705**. Measured reliability 2026-10-13 on Base `/fetch/basic`: PayAI 10/10 (at the cached $0.0006 that CDP refuses) and CDP 10/10 (at the full $0.002) settled first try. `/credits/buy` is never seeded (billing action, not a data product).
- **`serviceName` / `tags` / `iconUrl` are `RouteConfig` fields, NOT bazaar-extension fields** (`SERVICE_NAME` in `config.ts` and each definition's `catalogTags`, applied in `createPaymentConfig`). Put them inside `declareDiscoveryExtension()` and they silently never reach the catalog record — the extension preserves unknown keys, so the value still shows up in the 402 header and is echoed back by `/validate` under `bazaarExtension.serviceName`, which looks like confirmation but is not (x402-foundation/x402#2112). Catalogs write the record **at settle time**, so metadata must be deployed *before* seeding or refreshing it costs another payment per route. `catalogIconUrl()` forces https for non-local hosts because `wrangler dev` reports the configured route host over plain http.
- `patches/@x402__extensions@2.28.0.patch` (pnpm patch, wired in `pnpm-workspace.yaml` `patchedDependencies`): `@x402/hono`'s middleware runs an advisory Ajv validation of each route's bazaar extension on cold start, but Ajv compiles schemas via `new Function` — forbidden in workerd — which spammed a paired error+warn per paid route per isolate in production logs. The patch passes `logger: false` to Ajv and treats the codegen-disallowed `EvalError` as "skip validation" instead of a failure. It also guards the **payment-identifier** extension validator (new in 2.20+, same Ajv pattern) — unguarded, a payer attaching a schema to that extension would get a false `valid: false` on the payment path, not just log noise. The erc20-approval-gas-sponsoring Ajv call is facilitator-only code WebLens never reaches — left unpatched. Discovery itself was never affected (the extension is not dropped on validation failure). Upstream tracks this as x402-foundation/x402#3029 with open PR #3093 (same approach: detect the codegen error, skip validation, report once; both still open as of 2026-10-07) — on every `@x402/*` upgrade, re-key the patch (`pnpm patch @x402/extensions@<ver>` → re-apply the same edits, which locate the two validator functions by name since esbuild chunk filenames change between releases → `pnpm patch-commit`, then delete the old patch file) or drop it if #3093 has shipped. **Never just delete the `patchedDependencies` entry when a bump makes pnpm reject it** (the key is an exact version and `allowUnusedPatches` defaults to false, so a bump fails the install until the patch is re-keyed). The 2.24.0→2.28.0 bump removed the entry instead, and the log spam was back in production the same day. `tests/unit/x402-extensions-patch.test.ts` now fails the build unless the entry matches the installed version and the installed code carries the guard.
